Role

Act as senior software architect, full-stack engineer, database engineer, security engineer, QA engineer, and technical project manager for harewa-dev.

Non-negotiable product rules (Harewa)

From .cursor/rules/customer-vs-tailor-sections.mdc:

  • Customers (client preset): storefront + /profile only. Shop, cart, checkout, customize, Find a Tailor (/tailors), campaign join (/join/[slug]), measurements from profile.
  • Tailors (tailor Membership preset): /tailor/* only. Home, jobs, campaigns, notifications, dashboard. Default after sign-in: /tailor/home. Header “Store” may open /home.

  • Do not put customer orders/wishlist inside the tailor dashboard.
  • Do not weaken RBAC so customers can manage tailor clients or campaigns.

Non-negotiable RBAC rules (from the architecture doc, mapped)

  1. Authorization uses permission codes, never role names.
  2. UI hiding is not security. Every mutating API re-checks server-side.
  3. Never trust client-supplied orgId / account_id / ?orgId=.
  4. Company A and Company B never share roles, teams, or org-scoped records.
  5. Roles/templates are unique per tenant: (orgId, name).
  6. Every staff list, detail-by-id, report, export, and API that is org-scoped must apply tenant filter; ownership-capable resources also apply visibility (companyWideView).
  7. Do not create a second RBAC system. Extend Organization + Membership + RoleTemplate + P.*.

Explicitly out of scope (do not build)

  • /api/v1/ offline sync
  • Django /auth/security/roles URL tree
  • SubUser dual-password login / acting_as_team_member_id

1.4 Mental model (Harewa, after alignment)

Organization  (tenant = Account)
  ├── Membership[]     userId + orgId + rolePreset + roleTemplateId
  │                      + permissionsOverride[] + companyWideView + status
  ├── RoleTemplate[]   unique (orgId, name); permissions[]
  ├── org-scoped business rows (Product, Fabric, Category, Order, TaxSettings, …)
  └── TailorProfile[]  provider studio, orgId required

User
  ├── role: admin | client   (seller archived → treated as client)
  ├── optional Membership(s)
  └── user-scoped rows: Cart, Wishlist, Wallet, Profile, Notification, Customization
      isolation: userId === JWT sub   (NOT org-scoped)

JWT claims (staff/tailor with membership)
  sub, role, preset, permissions[], orgId, membershipRole, companyWideView, av (authzVersion)

Layer 1 TENANT (staff org-scoped resources):
  WHERE orgId = actor.orgId
  Cross-tenant → 403 "Cross-tenant access denied"

Layer 2 VISIBILITY (when companyWideView === false AND model has owner field):
  AND createdById/seller/user = actor.sub
  platform_admin → always company-wide (true)

Clients without Membership:
  JWT expands from User.role → client preset (*_own permissions)
  orgId may be null
  storefront catalog still uses DEFAULT_ORG_ID

PART 2 — Complete scope

2.1 In scope (the feature)

  1. Make Organization the explicit Account equivalent (documented + invariants).
  2. Multi-company registration / onboarding: a company can register (create a new Organization + first platform_admin Membership), then manage its own /admin dashboard, RoleTemplates, team members, permissions (from P.*), and org-scoped records — isolated from every other company.
  3. Harden Membership lifecycle (invite, create, edit, revoke, hard-delete, last admin).
  4. Harden RoleTemplate CRUD and assign (grant ⊆ actor, org-scoped).
  5. Keep P.* catalog, presets, nav, and API_PERMISSIONS in lockstep.
  6. Apply actor.orgId on every staff-scoped resource consistently.
  7. Apply companyWideView=false own-row filters on ownership-capable staff resources.
  8. Keep user-scoped commerce isolation (user === sub) unchanged.
  9. Keep tailor vs customer vs staff surfaces separate.
  10. Put reliable org context on ActivityLog writes.
  11. Sync bootstrap scripts and README with Prisma reality (bootstrap remains valid alongside self-serve registration).
  12. Extend yarn verify-rbac for CWV + members + cross-tenant + two registered companies isolation cases.

2.2 Out of scope (repeat)

  • ERP Part B modules
  • Org switcher UI (in-session hop between memberships) — registration of a new company is in scope; switching is not
  • SubUser dual login
  • Blocking customer storefront behind is_approved
  • Full Company Profile / bank accounts ERP screens unless already implied by existing org settings (do not invent a new ERP module)

2.3 Uncertainties (do not silently invent)

  1. Organization.ownerUserId: add only if it is a non-breaking, clearly useful invariant (e.g. first platform_admin from company registration). Prefer documenting “Company Admin = platform_admin membership” if owner FK would confuse tailor + staff.
  2. is_approved: do not lock the public shop. If added, it may only affect staff/org operational unlock — default is do not add unless Phase 1 analysis shows a clean fit with OrgStatus. New companies default to status: active unless a deliberate ops gate is designed.
  3. Company Profile: reuse Tax/AI/Shipping; do not create a parallel branding ERP. Registration collects minimal org identity (name, slug) only.
  4. Session terminate hub: Harewa already invalidates via authzVersion + refreshTokenJTI. Only add list/terminate UI if it cleanly fits /admin/users. Default: document existing invalidation; do not ship a half-built security hub.
  5. Company registration path shape: prefer a dedicated route (e.g. /register-company + POST /api/orgs/register or /api/auth/register-company) separate from customer /signup. Do not overload customer signup with role: admin. Existing signed-in clients without staff Membership may be allowed to “create a company” and receive platform_admin on the new org — document the chosen rule in Phase 1/4.

4.9 Request pipeline (Harewa vs doc)

Doc order: session → auth → company context → approval gate → audit.

Harewa:

  1. Browser hits page → src/proxy.ts verifies access-token (edge, no DB)
  2. Page uses authStore.can() for UI
  3. API: cookie JWT → requireAuth (sync) or requirePermissionFresh (reload Membership)
  4. Staff: requireActorOrgId then filter/stamp
  5. Errors: authErrorToResponse + optional ActivityLog denial

5.2 Create admin (bootstrap)

yarn ensure-default-org then yarn create-admin.
Creates platform_admin Membership on default org, CWV true.
This remains the ops path for the storefront / default Harewa org — scripts, not middleware. Self-serve company registration (§5.2b) is the product path for additional companies.

5.2b Company registration / onboarding (IN SCOPE)

BEFORE: rate limits; customer /signup stays customer-only.
START: dedicated company registration (page + API) — not customer /api/auth/signup.
DURING (single transaction preferred):
1. Create or link User (email unique; password hashed; verification policy as decided in Phase 4).
2. Create Organization: unique slug, status: active, isDefault: false (never claim the storefront default org).
3. Create Membership: rolePreset: platform_admin, companyWideView: true, status: active.
4. Issue JWT with that membership as primary (orgId = new org).
SUCCESS: redirect to /admin — company can create RoleTemplates, invite team, manage own records.
FAILURE: 400 duplicate email/slug; 403 blacklisted.
SECURITY: server generates org id; never trust client orgId; grants come from platform_admin preset only at birth.
ISOLATION: Company B’s staff never see Company A’s rows (Phase 2 filters).
OUT: no in-session org switcher.

5.3 Login

Authenticate User. Resolve primary membership (storefront org active, else oldest active).
If tailor preset → default /tailor/home.
If staff → /admin.
Else → /home.
Set JWT: permissions, orgId, companyWideView, authzVersion.

Suspended/revoked/invited must not fall back to full admin via User.role.

5.4 Invite member

Admin POST /api/admin/members with email, preset, optional template, override, CWV.
Grants ⊆ actor. Cannot grant CWV if actor lacks it.
Creates/links User + Membership. Invited status sends email.
List always scoped to actor.orgId.

5.5 Edit role

PATCH member. Exact permission replace via preset/template/override (no auto-adding dependency perms).
Bump authzVersion, clear refresh JTI. Target must re-login.
Editing self should force logout (existing UI behavior).

5.6 Revoke / hard delete

Soft revoke: status revoked, invalidate sessions.
Hard delete: platform_admin + users:delete; blacklist email/phone; refuse if user has other org memberships.

5.7 Staff catalog write

POST product: stampActorOrgId, set createdBy from actor, never body.orgId.
GET ?scope=staff: actor.orgId + CWV own-scope.
Public GET: storefront org only.

5.8 Cross-tenant

Admin of org A requesting org B product/order id → 403, not 200 with leaked data. Prefer 403 Cross-tenant access denied (existing). Do not leak existence via mismatched 404 unless that is already the route’s pattern — stay consistent per route.

5.9 Tailor vs staff

Tailor Membership: not isStaffPreset. Proxy allows /tailor/*. Staff may preview tailor pages; APIs still enforce TailorProfile ownership for edits. Admin /api/admin/tailors* uses actor.orgId.
