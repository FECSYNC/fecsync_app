What is partial / wrong in code vs the prompt's known facts:
- `PartyGuestRole` is NOT used by `PartyGuest`; it is used by `BookingGuest.partyRole`. It stays untouched. `PartyGuest` gets the new `kind PartyGuestKind` column (default `kid`); there is no host/guest mapping to migrate.
- API_PERMISSIONS entries for party routes say `bookings:read/write`, while the routes enforce `parties:read/write`. Fixed in S1-D3.
- Legacy party creation through `createBooking` treats the party line qty as heads (public hold qty 4 = 4 heads, per-head price). Kept for legacy rows: a legacy-created detail gets `kidCount = party line qty`, `adultCount = 0`, so heads stay identical to before.
- `ops_manager` currently holds `bookings:export`; S1-D2 says ops_manager must NOT have export, so it is removed.
- `BookingSettings.pastEditGraceMinutes` exists, and `assertBookingNotPastLocked` already implements the rule; party edits reuse it and map the error to `PARTY_PAST_LOCKED`.
- `Booking.confirmationSentAt` already exists, so `PartyBookingDetail.confirmationSentAt` is NOT added.
- The pending migration folder `prisma/migrations/20261028160000_guest_marketing_automation` is empty (no `migration.sql`), so `prisma migrate deploy` cannot run. The party migration is applied with `prisma db execute` + `prisma migrate resolve --applied`.
- No TypeScript exhaustive maps exist for `ActivityEntityType`; `NotificationType` has one client union in `src/services/notifications.ts`.

What is missing:
- Party enums, PartySettings / PartyPackageConfig / PartyMenuItem / PartyFoodOrder / PartyFoodLine / PartyBalanceReminder, the extra columns on the four thin party tables, `src/lib/parties/**`, the party engine, all new staff/public/me APIs, party money sync, ops-status sync, room conflict locking, party catalog screens, services/hooks, smoke.

What needs connecting:
- Booking engine status changes (hold, reserve, confirm, pending_payment, cancel, reactivate, TTL expiry, refund, webhook confirm) must call `syncPartyOpsFromBooking`.
- Every money path (`updateBookingAmountsAfterPayment`, refunds, POS settle in `saleEngine.ts`, `pos/webhook.ts`, `pos/http.ts`) must call `syncPartyMoney`.
- Engine heads (credentials + ticketsPerMonth meter) must use `kidCount + adultCount` for party bookings.
- Room conflict lock must live in the engine hold path so staff, public, POS, and reactivate all share it.
- Waiver sign/void must recompute `waiverMissingCount`.

Design decisions (stick to these):
- Session capacity for a party package counts parties per slot: the package line has qty 1 and holds 1 seat of the session. Extra-kid / extra-adult lines are `party_package` lines without a session (no capacity), priced from the package's `extra_kid` / `extra_adult` price bands (kept in sync with `PartyPackageConfig.extraKidPriceCents` / `extraAdultPriceCents`). Food lines are `add_on` lines with no product (band `party_food`).
- Credential policy: on confirm, unused `TicketCredential` rows are issued for `kidCount + adultCount`; count edits resize them (void extras, issue missing) and never touch redeemed ones. The `ticketsPerMonth` meter counts the same heads once (party lines are excluded from the qty sum; heads come from `PartyBookingDetail`).
- Room occupancy: a party occupies its room for `[visitStartsAt, visitEndsAt)` while the booking is hold / reserved / pending_payment / confirmed, or while the party is `checked_in` / `in_progress` (a refund after the party started does not free the room).
- Legacy guest replace (PATCH guests without `kind`): entries with no kind are stored as `other`, which only counts toward the package max and room cap. New endpoints default `kind` to `kid` and enforce kid/adult caps strictly.
